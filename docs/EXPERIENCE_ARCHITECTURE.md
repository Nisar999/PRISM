# PRISM Experience Architecture

## Overview
This document defines the interaction philosophy and User Experience (UX) architecture for PRISM. It serves as the UX source of truth, dictating the behaviors, workflows, and interaction models that all current and future PRISM interfaces (Desktop, Web, Mobile, CLI) must follow.

The core tenet is **One Mind. Infinite Shapes.** PRISM is the intelligence. The interfaces are the experience.

---

## 1. Experience Principles

### How PRISM Should Feel
- **Authoritative yet Transparent**: PRISM is an Agentic Intelligent Workspace. It should feel robust, exact, and predictable. When it takes action, it does so with confidence, but it always exposes its reasoning.
- **Calm Computing**: The interface respects the user's attention. Information is progressively disclosed. It does not demand attention through aggressive notifications or movement unless absolutely necessary.
- **Local-First & Private**: Interaction models should assume zero latency for local actions. Offline capabilities are a first-class experience, not an edge case.
- **Keyboard-First Workflow**: The system is designed for power users and developers. Every action, navigation, and command must be accessible via keyboard shortcuts and the Command Palette.
- **Decoupled Experience**: Interfaces never contain business logic. They strictly visualize the state of the PRISM Kernel and transmit user intents.

---

## 2. Application Structure

### Global Layout Philosophy
PRISM adheres to an App Shell model emphasizing stability and spatial memory. Per the Product Constitution, **PRISM Desktop is the product**; the VS Code editor is an embedded editing engine — not the outer shell.

The layout is divided into predictable regions:
- **Top Bar**: System status (Kernel connection, Milly state, active profile) and global window controls.
- **Global Sidebar**: Primary navigation across locked product surfaces — Dashboard, Milly, Memory, Thoughts, Planning, Execution, Workspace, and VS Code Editor (plus Settings as a system surface).
- **Main Workspace**: The dynamic content area, consisting of contextual panes (including the embedded editing engine when code work is active).
- **Status Bar**: Low-level metrics (memory usage, queue depth, background tasks).

### Navigation Hierarchy
Navigation is strictly hierarchical:
Global Area -> Workspace/Project -> Session -> Artifact/View.

### Panel Architecture
The Main Workspace utilizes a flexible pane system.
- Panes can be split horizontally or vertically.
- Panes contain specific views (e.g., Code Editor, Thought Log, Execution Graph).
- Panes are resizable, collapsible, and dockable.

### Context Preservation & Focus
- **State Persistence**: Switching between workspaces or global areas must preserve exact scroll positions, open panels, and active selections.
- **Focus Management**: The system explicitly tracks the "focused" pane. Keyboard commands implicitly target the focused pane unless a global modifier is used.

---

## 3. Workspace Model

The Workspace is the primary container for a specific cognitive context.

- **Projects**: Logical groupings of related sessions, artifacts, and context (e.g., "Frontend Refactor", "Database Migration"). Projects isolate memory retrieval contexts.
- **Sessions**: A single continuous engagement with PRISM to achieve a Goal. Sessions track the linear progression of intents, strategies, and executions.
- **Artifacts**: Durable outputs generated by PRISM (e.g., code files, markdown documents, architectural diagrams). Artifacts live within Projects and can span across Sessions.
- **Conversations**: Dialogue is treated as an input mechanism to clarify intent, not the primary deliverable. Conversations are transient interfaces to build the Goal, rather than infinite scrolling chats.
- **Tool Outputs**: Execution results (stdout, stderr, diffs) are attached to specific Execution Tasks within a Session.
- **Memory Visibility**: The Workspace must visually indicate which memories, skills, and context fragments are currently active and influencing PRISM's reasoning.

---

## 4. Navigation Model

- **Sidebar Behavior**: The global sidebar provides quick access to macro-areas. It can be collapsed to an icon-only state for deep focus.
- **Breadcrumbs**: The top of the Main Workspace always displays a breadcrumb trail (e.g., `Project Name / Session ID / Artifact Name`), providing spatial orientation and quick upward navigation.
- **Command Palette (`Ctrl+K` / `Cmd+K`)**: The primary mechanism for global search and execution. It supports fuzzy matching for workspaces, sessions, artifacts, and system commands.
- **Quick Switching**: Dedicated shortcuts to toggle between the most recently used workspaces or panes.
- **History Navigation**: Standard forward/backward navigation (similar to a browser) must be supported within the workspace to traverse artifact links and session history.

## 5. User Journey

The standard lifecycle of interacting with PRISM follows this path:

1. **Launch**: The interface connects to the PRISM Kernel. The splash screen visualizes boot sequence and registry loading.
2. **Workspace Selection**: The user selects an existing Project or creates a new one, establishing the Context Engine boundary.
3. **Intent Formulation**: The user expresses an intent (via prompt, command, or clicking a predefined Goal).
4. **Reasoning Visibility**: The UI renders the Cognitive Pipeline actively working: Intent -> Strategy -> Context -> Planner -> Router. The user sees Milly transition to a "Thinking" or "Planning" state.
5. **Tool Execution**: The Tool Orchestrator outputs an Execution Plan. The UI visualizes the dependency graph. As the Execution Runtime processes tasks, nodes in the graph light up (Running -> Succeeded).
6. **Artifact Generation**: Outputs are materialized as Artifacts. The interface opens the generated Artifact in a new pane for review.
7. **Memory Creation**: The user reviews the work. Successful execution paths are explicitly saved to the Memory Engine. The UI shows a confirmation of "Memory Indexed."
8. **Session Persistence**: The user closes the application. The session is safely suspended and persisted locally, ready to be instantly resumed.

## 6. Interaction Rules

### Loading & Streaming Philosophy
- **No Artificial Delays**: Never fake a loading state. Render state changes exactly as fast as the Kernel provides them.
- **Streaming over Batching**: Token streams from LLM providers must be rendered in real-time. Execution logs must stream line-by-line.
- **Skeleton States**: Use layout-matching skeleton loaders instead of generic spinners when waiting for data to populate structural panes.

### Handling Interruptions & Long-Running Tasks
- **Background Execution**: PRISM is designed for asynchronous autonomy. If a task is estimated to take a long time, the UI must allow the user to minimize the session and work on something else.
- **Non-blocking UI**: The Main Thread (UI) must never freeze during background execution.
- **Pause & Resume**: Users must be able to pause an active Execution Session via the UI, modifying the plan or context before resuming.

### Error Presentation
- Errors are not failures; they are data.
- **Inline Errors**: Display exact stack traces and failure reasons directly on the failed Tool Execution node.
- **Recoverability**: Always offer an actionable path forward (e.g., "Retry Task," "Modify Plan," "Provide Manual Input").

---

## 7. Multi-window Philosophy

As a professional tool, PRISM must support complex multi-monitor workflows.

- **Workspace Windows**: Users can tear off a Project into a separate OS-level window.
- **Floating Panels**: Specific panes (e.g., a live preview, a terminal tail) can be detached and floated.
- **Detached Artifacts**: Complex artifacts (like a large mermaid diagram or a massive JSON response) can be opened in dedicated windows.
- **Cross-window Synchronization**: All windows must reflect the same underlying Kernel state instantly via the Event Bus. Updating a setting in Window A immediately reflects in Window B.

---

## 8. Accessibility Principles

- **Contrast & Legibility**: Strict adherence to WCAG AA standards. High contrast mode support is mandatory.
- **Keyboard Traversal**: Every interactive element must be reachable via `Tab` navigation. Focus rings must be highly visible and distinct.
- **Screen Readers**: All critical state changes (e.g., "Task Failed", "Memory Indexed") must be announced via ARIA live regions.
- **Motion Reduction**: Users must be able to disable all non-essential animations (including Milly's fluid states).

---

## 9. Anti-Patterns

To maintain the architectural vision, PRISM interfaces must NEVER adopt the following UX patterns:

1. **The Chatbot Default**: Do not present a blank chat input and an empty message thread as the primary interface. PRISM is an Agentic Intelligent Workspace, not a messenger or ChatGPT clone. Chat is a modality, not the architecture.
6. **IDE Inversion**: Do not invert the product hierarchy into “VS Code + PRISM”. PRISM Desktop owns the application; VS Code owns editing UX only.
2. **Hidden Magic**: Never hide the tools, models, or context PRISM is using. If a decision is made, the UI must provide a way to inspect *why*.
3. **Destructive Defaults**: Never default to destructive or non-reversible actions (like overwriting a local file) without an explicit user confirmation or a visual diff review.
4. **Cloud-Tethered UX**: Never design a workflow that breaks or blocks if the user loses internet connection. Local execution and local memory are the baseline.
5. **Simulated Humanity**: Never use typing indicators (`...`), artificial delays, or conversational filler phrases ("Let me think about that...") to simulate human behavior. PRISM is an advanced machine; let it behave like one.
